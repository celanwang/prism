## 边界

- 硬件边界按 DESIGN 执行：CPU/MPS 真实测量；CUDA 与多卡主题只做解析模型
  和模拟器，报告中标注边界。不把模拟结论表述为实测结论。
- 测量协议先行：任何优化阶段的"收益"必须用 P0 协议测量，且附基线对照；
  单次运行、无分位数、无环境记录的数字不算证据。
- 研究问题驱动：新增优化或新主题必须先在任务规格中写明"要回答的问题"
  和"可能的失效形式"，不为凑方法数量而比较。
- 正确性、独立测试、完整记录不降级；模型规模、序列长度、并发数可以降级。
- 依赖最小化：基础实现只依赖 NumPy；PyTorch 等仅作参考对照，锁版本。

## 工程约定

- Python 3.12 + uv；`uv sync --locked`、`pytest`、`ruff check`、`ruff format --check` 全绿才允许提交。
- 提交格式 `feat(scope): ...` / `fix(scope): ...` / `docs: ...`，正文包含行为、证据和限制。
- 每个完成模块单独提交；阶段末汇总验收报告（`results/p<N>/REPORT.md`）。
- 长耗时基准以"可重复运行的配方 + 配置"交付，执行记录与产物入 `runs/`，
  正式证据摘要入 `results/`；不把 smoke test 当作阶段完成。

## 协作流程摘要（全文见 AGENTS.md）

1. Kimi（规划层）把阶段拆成原子任务，写任务规格：研究问题、改动白名单、
   禁止事项、验收命令、汇报要求。
2. Codex（执行层）在 `codex/<topic>` 分支按规格实现，跑测试后开 PR。
3. Kimi 独立验收：审 PR diff、亲自重跑验收命令、比对结构化汇报；
   不通过则带具体反馈打回，同一任务返修不超过 3 次，超限重新规划。
4. 高风险任务（公共接口、测量协议本身）先经 read-only 计划预审再放行执行。
